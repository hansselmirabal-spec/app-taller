## Exploration: Agregar Mecánica manual al Kanban Operativo + Pausa libera técnico

### Current State

**Backend — tracking init/lifecycle** (`apps/api/src/modules/tracking/tracking.service.ts`)
- `BODYSHOP_PARALLEL_CODES = new Set(['MECHANIC', 'DIAMANTADO', 'LLANTAS', 'ELECTRICO'])` (line 32) — confirmed scope for Func. 1.
- `initForBodyshop(entryId, processes[])` (178-206): guarded by `if (existing) return;` on ANY log for that sourceId — it's create-once, not additive. No `addProcess()` method exists anywhere in the codebase (confirmed via grep — no `addProcess`/`add-process` hits outside an unrelated presupuesto page).
- `POST tracking/init/:sourceType/:sourceId` (`tracking.controller.ts:111-120`) only re-triggers `initForMechanic` for `sourceType==='mechanic'`; does nothing for bodyshop. Confirmed no other endpoint creates additional TrackingLogs post-creation.
- `blockProcess()` (294-308): sets `status='blocked'`, `blockedReason`, `pausedAt`, calls `setPauseStatus(sourceType, sourceId, true)` which flips `Appointment.status`/`BodyshopEntry.status` to `'paused'`. **Never touches `log.technicianId`.**
- `unblockProcess()` (310-336): restores status, accumulates `pausedDurationMinutes`, restores entry/appointment status if no other blocked log remains. **Never touches `log.technicianId`, no availability check, no confirmation step.**
- `resolveAssignedTechnician()` (133-148) + conflict-check in `startProcess()` (256-265): the ONLY existing "is this technician busy" mechanism — a simple query `logRepo.findOne({ where: { technicianId, status: 'in_progress' } })`. A `'blocked'` log does NOT count as a conflict, so a technician with a paused process can start work elsewhere today while still nominally "owning" the paused log — this is exactly the gap Func. 2 must close.
- `BODYSHOP_PROCESS_ORDER`/`BODYSHOP_PROCESS_NAMES` (13-29) list all 6 real MOTHER-flow-relevant codes (BODYWORK, PREP, PAINT, POLISH, MECHANIC, FINAL_CONTROL) — MECHANIC is process-typed `PARALLEL` per `BODYSHOP_PARALLEL_CODES`, confirming it participates in both classifications (real capacity process AND parallel-scheduling process).

**Backend — technician availability (3 separate, non-unified implementations)**
1. `TrackingService` conflict-check (see above) — binary "is this tech `in_progress` on ANY log right now" — source-type agnostic (works for mechanic and bodyshop), the simplest and most directly reusable mechanism for "is the previously-assigned technician still free to resume".
2. `BodyshopService.getTechnicianAvailability(workshopId, date)` (905-984, exposed at `GET /bodyshop/tech-availability`) — computes `hoursFree`/`overhour` per technician for a given date, but **scoped to `BALANCE_PROCESSES = ['BODYWORK','PREP','PAINT','POLISH','FINAL_CONTROL']` only — does NOT include MECHANIC or any PARALLEL code**. Used today for the entry-creation auto-assign flow and by the frontend `ProcessTechRow` picker (see below) via `useDailyCapacity`.
3. `CapacityService.getDailyCapacity` (`apps/api/src/modules/capacity/capacity.service.ts`, exposed at `GET /capacity?date&workshopId`) — generic per-technician daily capacity (dailyHours/availableHours), workshop-type agnostic, used by `useDailyCapacity` hook across appointments/mechanic/bodyshop/dashboard pages. Doesn't reason about which specific process/entry occupies the technician.

None of these three give "is MY specific technician free RIGHT NOW to resume THIS process" directly — the cheapest correct building block for the pause/resume feature is #1 (the existing conflict-check pattern), extended into a small reusable method, e.g. `isTechnicianFree(technicianId, excludeLogId)`.

**Backend — bodyshop entry creation and `entry.processes` jsonb** (`apps/api/src/modules/bodyshop/bodyshop.service.ts`)
- `create()` (147-350) builds `allProcesses` (203-210) — the 5 real BALANCE processes plus `extraProcesses` from budget — and writes it ONCE to `entry.processes` (jsonb column, line 248) inside the creation transaction. There is no other write site for `entry.processes` in the whole service (confirmed by reading the full file — `updateHours()` only recalculates `bodyworkHours/prepHours/paintHours` + calls `trackingService.syncBodyshopPlannedHours`, it never touches `entry.processes`).
- `entryHoursByProcess()` (621-635) — the single source of truth for capacity screens — reads `entry.processes` filtered to `BALANCE_PROCESSES` (BODYWORK/PREP/PAINT/POLISH/FINAL_CONTROL only). **MECHANIC is never read here**, so adding Mecánica manually will NOT affect `getDayCapacity`/`getWeekCapacity`/occupancy screens regardless of whether `entry.processes` is updated.
- However, the frontend util `sumBodyshopHoursWithExtras()` (`apps/web/src/lib/utils.ts:89-97`) DOES read `entry.processes` (any code not in `{BODYWORK,PREP,PAINT}`) to compute the "Total hours" shown on the status-based Kanban card (`kanban/bodyshop.tsx` → `BodyshopCard`). This exact desync (`entry.processes` vs `tracking_logs.planned_hours`) was already a QA-reported bug fixed once for `updateHours()` (see comment at `bodyshop.service.ts:536-539`, `tracking.service.ts:208-214`). **Conclusion for point 5: adding Mecánica via a bare new `TrackingLog` WITHOUT also appending to `entry.processes` jsonb will reproduce that same class of bug** — the "Total hours" card in `kanban/bodyshop.tsx` would under-report, while the Kanban Operativo (`seguimiento/kanban`) would show the correct total (it derives everything from `TrackingLog`s via `getBoard()`/`buildCard()`). Any new "add process" backend method must update BOTH `entry.processes` (jsonb) and create the `TrackingLog` row, in one transaction, mirroring the existing `syncBodyshopPlannedHours` precedent.

**Frontend — which Kanban is "Kanban Operativo"**
- `apps/web/src/app/(dashboard)/kanban/bodyshop.tsx` is a STATUS kanban (scheduled/in_progress/done/cancelled columns) — generic entry tracking, no process-level start/pause/complete controls. This is NOT the "Kanban Operativo" referenced by the user.
- `apps/web/src/app/(dashboard)/seguimiento/kanban/page.tsx` (2002 lines) is the actual "Kanban Operativo" — columns are process codes (`AGENDA`, `BODYWORK`, `PREP`, `PAINT`, `POLISH`, `MECHANIC`, `FINAL_CONTROL`, `__PARALLEL_BLOCKING__`, `__DONE__`, `__CANCELLED__`), sourced from `TrackingService.getBoard()`. This is where both Func. 1 and Func. 2 UI work belongs.
  - `KanbanCard` component (1221-1616) already renders a dedicated **"Paralelos" section** (1499-1553) listing `card.parallelProcesses` with inline start/pause/complete icon-buttons per parallel process — this only shows processes that ALREADY have a `TrackingLog` (i.e., MECHANIC only appears here if it was included at entry creation). This section header (`<p>Paralelos</p>`, line 1501) is the natural anchor point for a new "+ Agregar proceso" button — but if the entry has ZERO parallel processes yet, the whole block (`card.parallelProcesses?.length > 0` guard, line 1499) doesn't render at all, so the button needs its own always-visible slot on the card, not nested only inside the existing conditional block.
  - Pause flow: `isPausable` button (1596-1602, card-level) and the modal's pause button (1202-1208) both call `onPause(logId, processName)` → opens `PauseModal` (629-687, reason picker only, no technician field) → `onConfirm` → `usePauseProcess()` → `blockTrackingProcess(logId, reason)`. Confirmed: **no technician-related UI at pause time today**, matching the backend (`blockProcess` never touches `technicianId`).
  - Resume flow: `isBlocked` button in both card (1570-1575, "Reanudar") and modal (1174-1179, "Reanudar proceso") call `onUnblock(cp.logId)` **directly, with zero confirmation/selection UI** → `useUnblockProcess()` → `unblockTrackingProcess(logId)`. This is the exact entry point (`onUnblock` prop, threaded from the page-level component down through both `KanbanCard` and `CardDetailModal`) where a technician confirm/change step must be inserted for Func. 2. Same pattern exists for parallel-process resume (line 1524-1529, `onStart(p.logId)` used for both "Iniciar" and "Reanudar" on parallel rows — worth checking whether parallel resume should route through `onUnblock` instead, since parallel processes use `startProcess`/pending→in_progress semantics rather than blocked→ separately; needs design-phase clarification, not resolved by this exploration).

**Frontend — reusable technician-picker pattern** (`apps/web/src/app/(dashboard)/appointments/bodyshop.tsx`)
- `ProcessTechRow` (698-…) is the closest reusable UI pattern for "suggest + let user confirm/change technician": inline expandable picker sourced from `useTechnicians()` + `useDailyCapacity(entry.date)`, sorted by available hours, click-to-pick, includes a "Nuevo técnico" shortcut via `TechnicianCreateDialog`. It is scoped to `BODYWORK|PREP|PAINT` only (`PROCESS_PROCESS_KEY` map, line 694) and keys off `entry.date`/`useDailyCapacity`, which is the general capacity endpoint, not process-specific.
- `TechnicianAssigner` (487-689) is a simpler single-technician-for-whole-entry picker (used for `assignTechnician`, not per-process) — less relevant here.
- `TechnicianCreateDialog` (`apps/web/src/components/appointments/technician-create-dialog.tsx`) is a create-technician form, unrelated to selection/confirmation flows — not reusable for the "confirm or change on resume" modal itself, only usable as an escape-hatch inside a new picker if desired (matching the ProcessTechRow pattern).
- Neither pattern is wired to `MECHANIC`/PARALLEL processes or to the tracking module at all — a NEW technician-picker component/modal will be needed for the pause/resume flow, though it can copy `ProcessTechRow`'s interaction pattern (sorted list + click to pick + create-new escape hatch).

**Frontend — notifications/highlighting**
- No toast library is present anywhere in `apps/web/src` (grep for `sonner`/`useToast`/`toast(` returned zero files).
- `ActivitiesPanel` (`apps/web/src/components/kanban/activities-panel.tsx`) is a localStorage-backed comments/checklist/attachments widget, unrelated to system-generated events like "process added" or "process paused" — no event/notification bus exists to hook into.
- **Conclusion for point 6: there is no existing highlight/notification mechanism for newly-added or newly-paused processes to extend.** Any such indicator (e.g., a badge/ring on the card, or a toast) would be new UI, not a wire-up of an existing pattern. Recommend treating this as an explicit, separately-scoped nice-to-have rather than bundling it into Func. 1/2 — a simple, low-cost option is a CSS pulse/ring on the affected card for N seconds after `useAddProcess`/`useUnblockProcess` mutation success (same visual language already used for the "late" ring on `BodyshopCard`/`KanbanCard`), no new dependency needed.

### Affected Areas

- `apps/api/src/modules/tracking/tracking.service.ts` — needs new `addProcessToBodyshop(entryId, processCode)` (or similar) method (bypassing the `initForBodyshop` existing-guard) for Func. 1; needs `unblockProcess()` signature change to accept an optional confirmed `technicianId`/`technicianName` for Func. 2, plus a technician-availability helper reusing the existing `in_progress` conflict-check pattern.
- `apps/api/src/modules/tracking/tracking.controller.ts` — new endpoint for "add process" (e.g. `POST tracking/process/bodyshop/:entryId/add`); `unblockProcess` DTO needs optional `technicianId`/`technicianName` fields (mirrors existing `StartProcessDto`).
- `apps/api/src/modules/bodyshop/bodyshop.service.ts` — the new "add process" flow must also append to `entry.processes` jsonb (transaction, mirroring `syncBodyshopPlannedHours` precedent) to avoid reintroducing the known Kanban-total desync bug.
- `apps/api/src/modules/bodyshop/bodyshop-entry.entity.ts` — no schema change needed; `processes` jsonb already supports arbitrary `{code,name,hours}` entries (confirmed field at line 88).
- `apps/web/src/app/(dashboard)/seguimiento/kanban/page.tsx` — primary UI surface: new "+ Agregar proceso" button/selector on `KanbanCard` (and/or `CardDetailModal`), scoped to bodyshop cards missing one or more of the 4 PARALLEL codes; new technician confirm/change step inserted into the `onUnblock` handler path for both card-level and modal-level "Reanudar" buttons.
- `apps/web/src/hooks/use-tracking.ts` — new `useAddProcess()` mutation; `useUnblockProcess()` mutation signature extended to accept technician params.
- `apps/web/src/lib/api.ts` — new `addTrackingProcess(...)` API call; `unblockTrackingProcess(logId, technicianId?, technicianName?)` signature change.
- `apps/web/src/lib/utils.ts` — no change required for `sumBodyshopHoursWithExtras` itself, but its correctness depends on the backend keeping `entry.processes` in sync (see above).
- `apps/web/src/app/(dashboard)/appointments/bodyshop.tsx` (`ProcessTechRow`) — reference pattern only; not modified unless the team decides to generalize it for reuse in the pause/resume picker.

### Approaches

**Funcionalidad 1 — Agregar Mecánica manualmente**

1. **New dedicated endpoint + service method that inserts one `TrackingLog` and appends to `entry.processes`** — `POST tracking/process/bodyshop/:entryId/add { processCode, hours }`, validated against `BODYSHOP_PARALLEL_CODES` and against processes not already present for that entry (dedup check). Transactional write to both `TrackingLog` and `BodyshopEntry.processes`.
   - Pros: keeps `entry.processes` and `tracking_logs` consistent (avoids the known desync bug class); single clear extension point; small, auditable diff.
   - Cons: introduces a second write path for `entry.processes` beyond `create()`, needs care to keep them from drifting (should extract a shared private helper, not duplicate the array-building logic).
   - Effort: Medium.

2. **Just insert a `TrackingLog` (no `entry.processes` change), rely only on `tracking_logs` as source of truth going forward.**
   - Pros: smaller change, no transaction coupling with `BodyshopEntry`.
   - Cons: reproduces the exact class of bug already fixed once for hours ("Kanban showed 32.9h, Agenda showed 34.8h") — `sumBodyshopHoursWithExtras()` (used in `kanban/bodyshop.tsx`'s status board) would silently under-report totals for any entry with a manually-added process. Not recommended.
   - Effort: Low (but trades correctness for it).

**Recommendation for Func. 1**: Approach 1 (transactional dual-write). Add a "+ Agregar proceso" affordance on `KanbanCard` visible whenever `card.sourceType === 'bodyshop'` and at least one of the 4 `BODYSHOP_PARALLEL_CODES` is absent from `card.parallelProcesses`; a small popover/modal lets the user pick the missing code(s) + hours, then calls the new endpoint.

**Funcionalidad 2 — Pausa libera técnico**

1. **Extend `blockProcess`/`unblockProcess` in place**: on `blockProcess`, snapshot the previously-resolved `technicianId`/`technicianName` onto the log (already resolvable via `resolveAssignedTechnician`) and clear the "reservation" side (e.g., clear `BodyshopProcessTech`/leave `Appointment.technicianId` — needs a design decision on where "released" state lives, since `resolveAssignedTechnician` currently re-derives the technician from `BodyshopProcessTech`/`Appointment.technicianId` each time `startProcess` runs, meaning simply not touching those tables means the tech stays "reserved" there even if the log itself is blocked). On `unblockProcess`, accept optional `technicianId`/`technicianName` in the request DTO; if provided, persist it onto the log (mirroring how `startProcess` already accepts and persists an explicit technician); if not provided, the backend still restores the log without technician reassignment, and the frontend is responsible for defaulting the picker to "same technician if free" using the existing conflict-check query.
   - Pros: reuses proven existing mechanisms end to end (`startProcess`'s persisted `technicianId` on the log, `resolveAssignedTechnician`, the `in_progress` conflict-check); minimal new backend surface — just extend two existing DTOs/methods, no new tables.
   - Cons: "release capacity" is fuzzy without also touching `BodyshopProcessTech` — needs explicit design-phase decision on whether pausing a bodyshop process should also null out (or leave) the corresponding `BodyshopProcessTech.technicianId` row, since that table is what `getTechnicianAvailability`/`getDayCapacity` read to compute "occupied hours" per technician. If left untouched, the availability screens (`/bodyshop/tech-availability`, `/appointments/bodyshop` capacity panels) would still show that technician as occupied even though their process is paused — undermining the stated goal ("técnico queda disponible para otro trabajo") for anyone consulting those other screens, even though the `tracking.service.ts` `in_progress` conflict-check itself would correctly let them start elsewhere.
   - Effort: Medium-High (touches two backend modules — tracking + bodyshop — and needs a cross-module design decision).

2. **Narrow fix scoped only to `tracking_logs`, leave `BodyshopProcessTech`/`Appointment.technicianId` untouched.**
   - Pros: smallest possible change, matches literally what's described ("liberar la asignación del técnico" could be read as "the conflict-check no longer treats them as busy", which IS already almost true today except the log's own `technicianId` stays populated after block — actually confirmed: conflict-check filters `status: 'in_progress'`, and a blocked log is `status: 'blocked'`, so **the conflict-check already does NOT block a paused technician from starting elsewhere today** — re-verify with orchestrator whether the "gap" is purely about the suggestion/confirmation UX on resume, not an actual blocking bug).
   - Cons: doesn't touch `BodyshopProcessTech`, so any UI/report that reads that table (capacity screens, `ProcessTechRow`) will still show the technician as "assigned" during the pause window, which may or may not satisfy the business intent — needs explicit confirmation from the user on scope before design phase.
   - Effort: Low-Medium.

**Recommendation for Func. 2**: Re-confirm scope with the user before design: does "liberar la asignación" mean (a) purely UX — resume always asks/confirms technician, nothing else changes structurally (Approach 2, low risk, ships fast), or (b) the technician must also disappear from capacity/occupancy screens while paused (Approach 1, requires touching `BodyshopProcessTech` too, higher blast radius). The orchestrator's stated finding ("gap real que resolver con la reasignación al reanudar") reads as (a) — the resume-time confirm/change UX — which is the safer, smaller-footprint interpretation and is what this exploration recommends defaulting to, flagging (b) as an open question for the proposal/design phase rather than assuming it.

### Risks

- `entry.processes` jsonb is written in exactly one place today (`bodyshop.service.ts create()`); any new write path (Func. 1) must be carefully kept in sync with `TrackingLog` creation or it reproduces a bug class already fixed once (QA-reported hours desync).
- `BodyshopService.getTechnicianAvailability()` and `entryHoursByProcess()` are hard-scoped to `BALANCE_PROCESSES` (5 codes) and structurally exclude MECHANIC/PARALLEL codes — Func. 1 (adding Mecánica) will NOT show up in capacity/occupancy screens by design of the current code; if the user expects Mecánica-added-manually to affect capacity math, that's a separate, larger change (extending `BALANCE_PROCESSES`), not scoped by this exploration.
- Func. 2's "liberar técnico" has two plausible interpretations (UX-only confirm-on-resume vs. structural release from `BodyshopProcessTech`) with materially different effort/risk; must be disambiguated before `sdd-design`.
- No notification/highlight/toast infrastructure exists anywhere in the frontend; if either feature is expected to visually flag changes, that's net-new UI work with no reusable base.
- The "Paralelos" section on `KanbanCard` only renders when `card.parallelProcesses?.length > 0` — the new "+ Agregar proceso" affordance needs its own always-visible slot on the card, independent of that conditional, to be reachable when zero parallel processes exist yet.
- Parallel-process resume today reuses the plain `onStart(p.logId)` handler for both "Iniciar" and "Reanudar" (`seguimiento/kanban/page.tsx:1524-1529`) rather than routing paused parallel processes through `onUnblock` — needs clarification during design whether Func. 2's technician-confirm step must also apply to this parallel-resume code path (likely yes, since Mecánica itself is PARALLEL and is explicitly in scope for Func. 2).

### Ready for Proposal

Yes, with one explicit open question to carry into `sdd-propose`/`sdd-design`: confirm with the user whether "pausa libera técnico" (Func. 2) requires touching `BodyshopProcessTech`/capacity-screen visibility, or is scoped purely to the resume-time confirm/change UX plus the tracking_log's own `technicianId`. Recommend defaulting to the narrower UX-only scope unless the user says otherwise, given evidence that the `in_progress` conflict-check (the actual "can this tech start something else" gate) already ignores blocked logs today.
